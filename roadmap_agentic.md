# Roadmap: Agentic Neurosymbolic KG Builder

This document tracks the planned extensions to the current MVP, organized by implementation step.
Each step is designed to be independently mergeable and testable.

The overarching goal is to evolve the current linear LangGraph pipeline into a genuinely agentic,
neurosymbolic system with adaptive human-in-the-loop (HITL) — suitable for publication in a Q1 journal.

---

## Narrative Arc (for the paper)

Current state: **deterministic pipeline** with LLM calls and symbolic post-processing.
Target state: **reflective multi-agent system** where agents self-correct using symbolic constraints,
graph reasoning validates structural completeness, and human intervention is requested only when
confidence falls below empirically-tuned thresholds.

The three pillars of the contribution:
1. **Agentic**: self-correcting loops, specialized agents, supervisor orchestration
2. **Neurosymbolic**: symbolic constraints embedded in the reasoning loop (not just post-hoc filters)
3. **Adaptive HITL**: human effort is proportional to extraction uncertainty, not uniform across all cases

## Step 1 — Reflective Extraction Loop (LangGraph conditional edges)

**Status**: ✅ done (2026-03-30)

### What changes

Transform the current linear `StateGraph`:
```
extract → normalize → semantic_validate → schema_validate → END
```

Into a reflective loop with conditional routing:
```
extract → normalize → semantic_validate ──[issues found, retries < N]──→ re_extract (with feedback)
                                        └──[issues found, retries >= N]──→ human_review
                                        └──[no issues]──────────────────→ schema_validate → END
```

### Implementation plan

- Add `retry_count` and `last_issues` fields to `PipelineState` (ontology_pipeline.py)
- Add `re_extract` node: re-calls LLM with original text + structured issue list as feedback
- Add `human_review` node: flags state for operator intervention instead of auto-correction
- Replace `add_edge("semantic_validate", "schema_validate")` with `add_conditional_edges()`
- Configure max retries in `config.yaml` (suggested default: 2)
- The feedback prompt must include: issue code, affected entity, fix_hint from semantic validator

### What this enables for the paper

- First real "agentic" behavior: the system observes its own output and self-corrects
- Measurable: compare extraction quality with/without loop (precision/recall on held-out manuals)
- Cite: ReAct (Yao et al. 2022), Reflexion (Shinn et al. 2023)

### Files to modify
- `backend/services/ontology_pipeline.py`
- `config.yaml`

## Step 2 — Graph Reasoning with NetworkX

**Status**: ✅ done (2026-03-30)

### What changes

Add a dedicated graph analysis node to the LangGraph pipeline that uses NetworkX to:
1. Detect structurally incomplete chains (Symptom → FailureMode → CorrectiveAction)
2. Find orphaned nodes not reachable from the root Asset
3. Identify FailureModes with no RESOLVED_BY relation
4. Check that every Component referenced in AFFECTS actually exists
5. Detect invalid cycles in the relation graph

When gaps are found, the node produces structured `GraphIssue` objects with:
- `issue_type` (orphan | missing_relation | broken_chain | cycle)
- `affected_nodes` (list of IDs)
- `suggested_fix` (auto-generated by LLM or rule-based)

If the issue is high-confidence fixable (e.g., an orphaned node that matches an existing chain entity
by semantic similarity) → auto-fix and log.
If ambiguous → surface to human review.

### Implementation plan

- Add `networkx` dependency
- Create `backend/services/graph_reasoning.py` with:
  - `build_nx_graph(ontology_instance)` → `nx.DiGraph`
  - `detect_chain_gaps(G, schema)` → `list[GraphIssue]`
  - `detect_orphans(G)` → `list[GraphIssue]`
  - `suggest_missing_relations(G, ontology_instance, llm_client)` → `list[SuggestedRelation]`
- Add `graph_validate` node to LangGraph pipeline after `schema_validate`
- Add `SuggestedRelation` to `PipelineState` for HITL review
- Frontend: add a "Suggested Relations" review panel before export

### What this enables for the paper

- Symbolic reasoning on the KG structure — the "symbolic" in neurosymbolic
- Graph completeness metric: % of chains with no gaps before vs. after agent intervention
- Human only reviews suggested relations, not the full graph

### Files to create
- `backend/services/graph_reasoning.py`

### Files to modify
- `backend/services/ontology_pipeline.py`
- `frontend/app.js` (new review panel)
- `backend/routers/ontology.py`

## Step 3 — Confidence Scoring and Adaptive HITL

**Status**: not started

### What changes

Assign a `confidence_score` (0.0–1.0) to every extracted entity and triplet.
Use this score to route items to one of three buckets:
- `auto_approve` (score ≥ θ_high): accepted without human review
- `human_review` (θ_low ≤ score < θ_high): shown to operator for validation
- `auto_reject` (score < θ_low): discarded with reason logged

This makes HITL **adaptive**: the operator reviews only ambiguous cases.

### Confidence signal sources

For triplets:
- Semantic overlap between extracted text and source page (token overlap ratio)
- Number of source pages with corroborating evidence (`source_pages` count)
- Cross-chunk agreement (entity appeared in N independent chunks)
- Regex pattern match strength (strong verb match → higher confidence)
- Semantic validation: no issues → boost; issues present → penalize

For ontology nodes:
- Required fields present without human binding → higher confidence
- LLM extracted cleanly without retries → higher confidence
- Human binding required → lower confidence

### Implementation plan

- Create `backend/services/confidence.py`:
  - `score_triplet(triplet, page_texts, issues)` → `float`
  - `score_ontology_node(node, pipeline_state)` → `float`
  - `classify(score, theta_high, theta_low)` → `Literal["auto_approve", "human_review", "auto_reject"]`
- Attach scores to `Triplet` and ontology node models
- Add thresholds to `config.yaml` (θ_high default 0.80, θ_low default 0.45)
- Frontend: show confidence badge on each triplet card; pre-sort by confidence ascending
- Frontend: add "Auto-approve all high-confidence" bulk action button
- Log every auto-approve and auto-reject decision for auditability

### What this enables for the paper

- Key metric: operator review effort reduction (% of items auto-approved vs. baseline of 100%)
- Run on held-out manuals: measure precision/recall of auto-approved items vs. ground truth
- Adaptive HITL is a concrete contribution — not just "human in the loop" but "human where needed"
- Cite: human-AI teaming literature, active learning confidence thresholds

### Files to create
- `backend/services/confidence.py`

### Files to modify
- `backend/services/llm_service.py` (attach scores to triplets)
- `backend/services/ontology_pipeline.py` (attach scores to nodes)
- `frontend/app.js` (confidence badges, bulk approve)
- `config.yaml` (thresholds)

## Step 4 — Multi-Agent Architecture with Supervisor

**Status**: not started (depends on Steps 1–3)

### What changes

Decompose the current monolithic pipeline into **specialized agents** coordinated by a
**Supervisor agent** that decides when to escalate to the human.

### Agent roles

| Agent | Responsibility | Tools |
|---|---|---|
| `ScopingAgent` | Identify relevant sections from the manual | ToC parser, keyword scan, LLM |
| `ExtractionAgent` | Extract triplets and ontology from approved pages | LLM + schema constraints |
| `ValidationAgent` | Verify semantic and structural correctness | NetworkX, symbolic rules, LLM |
| `RefinementAgent` | Correct identified issues using structured feedback | LLM with feedback prompt |
| `Supervisor` | Route between agents, decide HITL escalation | Confidence scores, policy rules |

### Supervisor logic

The Supervisor is itself a LangGraph node with conditional routing:
```
Supervisor:
  if confidence(result) >= θ_high and no_critical_issues:
      → next_agent or END
  elif retries < max_retries and issues are auto-correctable:
      → RefinementAgent
  else:
      → HITL (human_review_node)
      → resume after human approval
```

The Supervisor communicates with the human through structured messages:
- What was attempted
- What the issue is
- What options the human has (approve / reject / edit / skip)

This replaces the current implicit HITL (fixed screens in the frontend) with an
**explicit, agent-driven escalation protocol**.

### Human communication interface

The Supervisor sends structured escalation messages:
```json
{
  "escalation_id": "esc-001",
  "agent": "ValidationAgent",
  "issue": "FailureMode FM-003 has no RESOLVED_BY relation. Suggested: link to CA-007 (confidence 0.72).",
  "options": ["approve_suggestion", "reject_suggestion", "provide_correction"],
  "context": { "node": "FM-003", "suggested_relation": "RESOLVED_BY", "target": "CA-007" }
}
```

The frontend renders escalation messages as structured decision cards, not generic form fields.

### Implementation plan

- Refactor `ontology_pipeline.py` into separate agent modules under `backend/agents/`
- Create `backend/agents/supervisor.py` with routing logic
- Create `backend/agents/scoping_agent.py`
- Create `backend/agents/extraction_agent.py`
- Create `backend/agents/validation_agent.py`
- Create `backend/agents/refinement_agent.py`
- Build a new top-level `StateGraph` in `backend/agents/orchestrator.py` that wires agents together
- Add `EscalationMessage` model to the shared state
- Frontend: replace static screens with dynamic escalation card rendering

### What this enables for the paper

- True multi-agent architecture — publishable as a novel system design
- Supervisor-as-HITL-coordinator is a concrete architectural contribution
- Measurable: compare number of escalations per manual before/after confidence scoring
- Cite: LangGraph multi-agent patterns, human-AI teaming, maintenance domain KG literature

## Implementation Order

```
Step 1 (reflective loop)
    ↓
Step 2 (graph reasoning)
    ↓
Step 3 (confidence scoring)
    ↓
Step 4 (multi-agent + supervisor)
```

Steps 1–3 are largely independent of each other and can be developed in parallel if needed.
Step 4 depends on all three, since the Supervisor relies on confidence scores (Step 3),
graph reasoning results (Step 2), and the reflective loop pattern (Step 1).

## Notes for the paper framing

- The system is **domain-agnostic**: the ontology schema is loaded from `ontology_schema.JSON`,
  not hardcoded. Any maintenance domain can be targeted by swapping the schema.
- The neurosymbolic framing is grounded: symbolic rules (regex, schema constraints, graph traversal)
  are **embedded in the agent reasoning loop**, not applied as a post-hoc filter.
- The HITL design follows the principle of **minimal necessary intervention**: the system asks
  humans only when it cannot resolve uncertainty autonomously within configured bounds.
- The export format (canonical JSON with `metadata`, `nodes`, `relationships`) is designed to be
  ingested by downstream graph databases (Neo4j, Oxigraph) without transformation.
